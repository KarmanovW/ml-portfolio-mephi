# Приоритизация обращений

Ранжирование назначенных обращений по вероятности успешного целевого действия в течение
5 дней после назначения. Метрика — **Daily Average Precision**: Average Precision считается
внутри каждой даты назначения и усредняется по дням.

## Запуск

```bash
pip install -r requirements.txt
jupyter notebook solution.ipynb
```

Ноутбук ищет данные по путям из `src/config.py` (каталог Kaggle, затем `data/` и текущий
каталог). На выходе — `submission.csv` с колонками `lead_id` и `score`.

## Структура

```
solution.ipynb        сценарий запуска: загрузка, признаки, обучение, submission
src/config.py         константы схемы данных, сиды, параметры валидации
src/metrics.py        Average Precision и Daily Average Precision
src/features.py       признаки из событий, отношения, скользящие перцентили, категории
src/validation.py     разбиение по дням с расширяющимся окном
src/models.py         обёртки LightGBM / CatBoost / XGBoost
src/blending.py       ранговое смешивание, жадный отбор, стекинг
```

## Подход

### Признаки

Готовые табличные агрегаты дают слабый сигнал: линейная модель на них едва превосходит
базовую частоту класса (0.26 против 0.21 Daily AP). Основной прирост даёт агрегация
`events.csv` — с ней та же модель выходит на 0.62.

Из событий строятся: объём и давность активности, счётчики и давность по каждому типу
события, окна 1/2/3/7/14/30 дней, доля high-intent действий (favorite / chat_open /
call_click), интервалы между событиями, время суток и доля выходных, траектория и разброс
просмотренных цен, гистограмма контекстов, тип и контекст последнего события.

Поверх табличных агрегатов добавлены отношения: ускорение активности (окно 7 дней к 30)
и конверсия прошлых обращений пользователя.

Отдельная группа — скользящие перцентили: позиция обращения относительно назначенных
в предыдущие 24 часа. Метрика сравнивает обращения внутри дня, поэтому относительная
позиция несёт информацию, которой нет в абсолютных значениях.

### Защита от утечки

Признаки из событий используют только записи с `event_ts < assignment_ts`: в исходных
данных примерно 6% событий относятся к моменту после назначения, при скоринге они
недоступны. Скользящие перцентили опираются только на обращения с более ранним
`assignment_ts`. Поля, описывающие будущий исход, не используются.

### Пропуски, категории, редкие значения

* **Пропуски** не заполняются. LightGBM, XGBoost и CatBoost обрабатывают NaN нативно,
  выбирая для него направление ветвления. Здесь это содержательно: пропуск означает
  отсутствие истории (например, обращение без предшествующих событий). Деление на ноль
  в производных признаках даёт NaN, а не ноль — нулевой знаменатель означает отсутствие
  базы для отношения, а не нулевое отношение.
* **Категории** хранятся как `category`: LightGBM и XGBoost работают с ними напрямую,
  CatBoost получает индексы колонок и применяет упорядоченное кодирование. One-hot не
  используется — он теряет информацию о частоте и раздувает пространство признаков.
* **Редкие значения**: категории с частотой в train ниже порога и значения, не
  встречавшиеся в train, схлопываются в общий токен, словарь категорий одинаков для
  train и test. На текущих данных минимальная частота категории — 77 наблюдений, поэтому
  правило ничего не схлопывает, но защищает от незнакомых значений в скрытом тесте.

### Валидация

Тест лежит строго позже train по времени (train до 22 апреля, test с 23 по 27 апреля),
поэтому случайное разбиение завышало бы качество: модель видела бы «будущие» дни.
Используется time-series CV с расширяющимся окном — обучение всегда на днях,
предшествующих валидационному блоку.

Шесть блоков по два дня покрывают последние 12 дней train. Блоки по два дня, а не по
одному, потому что Daily AP на единственном дне слишком шумна: бутстреп даёт 95%
доверительный интервал около ±0.04 на выборке размера теста.

Ранняя остановка идёт по Daily AP, реализованной как пользовательская метрика LightGBM,
то есть по целевой метрике задачи, а не по прокси.

### Модели

Пул из девяти моделей трёх семейств:

| Модель | Роль |
|---|---|
| `lgb_primary`, `lgb_alt` | LightGBM с двумя конфигурациями из Optuna |
| `lgb_trailing` | LightGBM на наборе со скользящими перцентилями |
| `lgb_dart` | LightGBM с dart-бустингом |
| `catboost_d6`, `catboost_d4` | CatBoost с разной глубиной |
| `xgb_clf` | XGBoost, классификация |
| `xgb_rank`, `lgb_rank` | ранжирующие постановки, группа — день назначения |

Гиперпараметры LightGBM подобраны Optuna (120 попыток) по Daily AP на отложенных
последних трёх днях train. Проход по всему CV внутри каждой попытки был бы в шесть раз
дороже; найденные конфигурации затем честно оцениваются на полном CV в составе пула.

Каждая модель переобучается на всём train и усредняется по пяти сидам — это снижает
дисперсию ранжирования.

### Смешивание

Предсказания переводятся в ранги: Average Precision зависит только от порядка объектов,
и ранги выравнивают разные шкалы моделей без калибровки.

Сравниваются два способа: жадный отбор с возвратом (метод Каруаны) и стекинг
логистической регрессией. Стекинг оценивается по схеме leave-one-fold-out — обучать
мета-модель на тех же OOF, на которых её оценивают, значит получить смещённую оценку.
Выбирается вариант с более высоким OOF Daily AP; на текущих данных это жадный отбор,
который распределяет вес между четырьмя-пятью классификаторами.

## Что проверялось и не вошло в решение

Проверено на той же схеме валидации, прироста не дало:

* **Отбор признаков** — 24 случайных подмножества размеров 40/90/140 и поочерёдное
  исключение семейств признаков. Полный набор устойчиво лучше: улучшения от урезания
  проявляются на одном окне валидации и меняют знак на другом, то есть являются шумом.
* **Ранжирующие постановки** как основная модель — при 16 днях в train групп слишком
  мало, обе модели уступают классификаторам и получают в отборе нулевой вес.
* **Сессионные признаки** (число сессий, переходы между типами событий) — ухудшали
  результат линейной проверки.
* **Признаки позиции** `src_slot` и `ctx_seq` — все дают одиночный Daily AP на уровне
  базовой частоты класса.
* **Взвешивание свежих дней** при обучении и обучение только на последних днях.

Диагностика потолка: обучение и предсказание на одних и тех же строках (полное
переобучение) даёт для линейной модели лишь 0.65, а добавление части того же дня
в обучение не улучшает предсказание остальных обращений этого дня. Это указывает на
ограничение со стороны сигнала в признаках, а не на неверную настройку модели.

## Воспроизводимость

Все источники случайности зафиксированы: `SEED` в `src/config.py`, сиды моделей,
сид сэмплера Optuna. Версии библиотек закреплены в `requirements.txt`. Повторный запуск
ноутбука на тех же данных и версиях даёт идентичный `submission.csv`.

## Использованные библиотеки

Открытые библиотеки, разворачиваемые локально, без обращений к внешним API:
pandas, NumPy, scikit-learn, LightGBM, XGBoost, CatBoost, Optuna.
Модель ансамблирования — жадный отбор Каруаны (Caruana et al., 2004).
